## Keputusan Lintas-Sektor

- **Grading server-authoritative, UX client-optimistic.** `GET /lessons/:id` tetap kirim data exercise lengkap (opsi + kunci jawaban) supaya `exerciseFactory.ts`/`lessonSession.ts` bisa dipakai ulang di browser untuk feedback instan per-soal. Tapi `POST /lessons/:id/attempts` **menghitung ulang skor di server** pakai fungsi `packages/domain` yang SAMA — skor yang disimpan/dapat XP selalu hasil hitungan server, bukan self-report client (perlu karena sekarang ada leaderboard antar-murid, tidak seperti app lama yang single-user/local-trusted).
- **`unlockRules.ts` ditegakkan di server**, bukan cuma di client — `LessonsModule` cek status unlock terhadap `UserLessonProgress` sebelum menerima attempt.
- **`packages/domain` tetap bebas dari Prisma** — fungsi murni, tidak tahu soal database; service di `apps/api` yang jadi lem ke Prisma.
- **Angka XP: PRD menang, tapi mekanismenya di-porting.** Formula lama pakai `10 + 1×correctFirstTry + 5×speakHighCount` + level curve `100×n`. PRD v4.0 (GAM-01/03) minta angka beda: lesson +10–30, checkpoint +50, percakapan +20, kuis harian +10, level curve `1000×n`. Sudah diimplementasi di `packages/domain/src/gamification/xpService.ts` dengan mapping bintang→XP ★=10/★★=20/★★★=30 — **PROPOSAL, perlu dikonfirmasi ke product owner** (PRD kasih rentang & tingkat bintang terpisah, tidak pernah eksplisit memetakan keduanya). `starsForScore(accuracyPercent)` juga sudah ada di file yang sama (ambang LP-03: 80-89=1, 90-99=2, 100=3) — tapi **belum ada yang MEMANGGIL fungsi ini** dari alur completion lesson sungguhan; itu tugas `LessonsModule` (Milestone 7, belum dikerjakan).
- **XP jangan dobel fungsi.** GAM-03 (level/leaderboard) butuh XP monoton naik; GAM-02 (beli streak-freeze pakai 50 XP) butuh XP jadi mata uang yang bisa dibelanjakan. Kalau keduanya pakai ledger yang sama, beli freeze bisa bikin rank turun — kemungkinan tidak diinginkan. **Keputusan:** `XpEvent` tetap ledger append-only selalu positif (sumber kebenaran level+leaderboard); pembelian freeze jadi counter terpisah, bukan `XpEvent` negatif.
- **Auth student vs admin benar-benar terpisah** — signing secret, audience, dan tabel refresh-token yang beda, bukan cuma route beda — supaya token murid yang bocor tidak bisa dipakai sebagai token admin. Sudah diimplementasi (`AuthModule` vs `AdminAuthModule`).

## 1. Struktur Monorepo

**pnpm workspaces + Turborepo.** Nx terlalu berat untuk graf sekecil ini (2 frontend Vite + 1 backend Nest + beberapa shared package); plain workspaces tanpa task runner berarti urutan build/caching harus diatur manual begitu CI masuk. Turborepo pas di tengah: orkestrasi `turbo run build|test|lint` lintas workspace + caching, cukup satu file config, gampang dilepas kalau suatu saat tidak perlu. pnpm dipilih karena `node_modules` yang strict (menangkap impor silang antar-paket yang tidak sengaja — penting supaya `packages/domain` tetap benar-benar decoupled).

```
<repo>/
├── apps/
│   ├── student/          # React + Vite + TS + Tailwind + shadcn/ui, PWA (vite-plugin-pwa)
│   ├── admin/             # React + Vite + TS + Tailwind + shadcn/ui (tanpa PWA)
│   └── api/               # NestJS
│       ├── prisma/{schema.prisma, seed.ts, seed-data/raw/unit_hiragana.json}
│       └── src/
├── packages/
│   ├── domain/            # logic murni hasil porting — TIDAK impor Prisma. Build step tsc->CommonJS
│   │                       # (BUKAN "TS-source-only" seperti draft awal plan ini bilang -- lihat
│   │                       # catatan "koreksi" di bagian bawah plan ini, penting dibaca)
│   ├── ui/                # primitif shadcn/ui + preset Tailwind + design token (shell doang, bukan fitur)
│   └── config/            # tsconfig/eslint/prettier/tailwind preset dasar
├── turbo.json
├── pnpm-workspace.yaml
├── docker-compose.yml      # lokal: postgres + redis + minio
└── .github/workflows/ci.yml
```

Tidak ada `packages/api-types` manual — lihat poin 7 (OpenAPI codegen) supaya tidak ada drift tipe frontend vs backend.

**KOREKSI PENTING dari draft awal plan ini:** draft ini semula bilang "tiap package workspace TS-source-only, tanpa build dist terpisah." Itu SALAH dan sudah diperbaiki saat implementasi: `apps/api` (NestJS) di-compile jadi JS lalu dijalankan `node dist/main.js` di produksi/Docker — proses `node` murni itu TIDAK BISA `require()` file `.ts` mentah. Jadi `packages/domain` (dan `packages/ui`) SEKARANG punya build step `tsc` sungguhan (`"build": "tsc"`, `main`/`types` menunjuk ke `dist/`), bukan menunjuk ke `src/`. `packages/domain` di-compile ke **CommonJS** (harus cocok dengan `apps/api` yang juga CommonJS — sempat salah coba ESM dulu, ketahuan lewat smoke test `require()` sungguhan yang gagal, lihat commit `458971b`). `packages/ui` boleh tetap ESM (`"type": "module"`) karena cuma dikonsumsi Vite (bundling, bukan `node require()` langsung).

## 4. Auth (SUDAH DIIMPLEMENTASI — `apps/api/src/auth/`, `src/admin-auth/`, `src/users/`)

- **Token undangan**: random opaque (`crypto.randomBytes(32).toString('base64url')`), yang disimpan cuma `sha256(token)` (`src/common/opaque-token.util.ts`) — bukan JWT (JWT tidak bisa di-revoke tanpa blocklist, padahal ADM-12 butuh resend/revoke).
- **Registrasi**: validasi token → hash password `argon2id` → `User` dibuat dengan `classId`/`email` dari `Invitation` yang tervalidasi di server (BUKAN dari body request) → invitation jadi `ACCEPTED` → langsung terbitkan access+refresh JWT (auto-login).
- **JWT**: `@nestjs/jwt`+`@nestjs/passport`+`passport-jwt`; access 1 jam, refresh 14 hari, secret terpisah student (`JWT_STUDENT_SECRET`) vs admin (`JWT_ADMIN_SECRET`). Rotasi refresh dengan deteksi-reuse: token yang sudah di-revoke tapi dipakai lagi → revoke seluruh chain, paksa re-login. Payload JWT `sub` juga dicocokkan dengan `userId`/`adminUserId` hasil lookup DB (pertahanan berlapis).
- **Rate limit/lockout**: lockout 5x-gagal→15 menit per-akun lewat Redis (`login_fail:{email}`/`login_lock:{email}`).
- **Lupa password**: `/auth/forgot` selalu balas 200 (no user enumeration). `/auth/reset` revoke SEMUA refresh token user itu.
- **BELUM ADA YANG BISA DITES END-TO-END SUNGGUHAN** — semua di atas cuma diverifikasi lewat typecheck+lint+unit-test util murni (tidak butuh DB). Perlu Postgres+Redis hidup untuk tes sungguhan (register→login→refresh→forgot→reset lewat REST client beneran).

## 6. Port AI-Tutor (`TutorModule`) — BELUM DIKERJAKAN (Milestone 11)

## 6b. Pipeline Audio TTS (`AudioModule`) — SELESAI (Milestone 8)

Implementasi di `apps/api/src/audio/`: `hashAudioKey(textJp, voice)` (sha256 dari `text|voice`, BUKAN cuma `sha256(text)` — sudah `hash(text+voiceId)` sejak awal, persis catatan di bagian 6 di atas soal `POST /tutor/speak`; `voice` sekarang baru `'female'|'male'`, akan diperluas ke voice ID per-karakter TutorModule begitu Milestone 11 digarap, tidak butuh migrasi skema baru) → `AudioService.resolveAudioUrl(textJp, voice)`: cek `AudioAsset` by hash, cache hit → balikin `s3Url` tersimpan (TIDAK panggil TTS provider lagi — diverifikasi), cache miss → generate (`TtsClient`) → upload (`ObjectStorageService`, S3-compatible) → `upsert` baris baru.

**Kapan dipanggil — SAAT SEED, bukan saat request.** NFR eksplisit minta API p95 < 300ms; generate TTS sinkron di dalam `GET /lessons/:id` akan melanggar itu telak (TTS + upload S3 bisa makan waktu detik-an). Jadi `seed.ts` memanggil `resolveAudioUrl` untuk tiap vocab/sentence SEKALI di waktu migrasi konten (best-effort, lihat di bawah); `ContentService.loadUnit` di request-time cuma melakukan SATU query bulk `AudioAsset.findMany({textHash: {in: [...]}})` (murah, baca-saja) lalu isi field `audio` domain Vocab/Sentence dari situ — kosong (`""`, placeholder jujur bukan url palsu) untuk teks yang belum pernah digenerate. Pola sama ini nanti dipakai TutorModule (Milestone 11) untuk `/tutor/speak`, TAPI di sana panggilannya on-demand/interaktif (balasan AI dinamis, tidak bisa di-pre-generate) — beda karakteristik dari audio konten lesson yang sudah diketahui sebelum murid membuka lesson-nya.

**Seam TtsClient/ObjectStorageService** (`tts-client.ts`, `azure-tts.client.ts`, `object-storage.service.ts`) sengaja nerima NILAI MENTAH di constructor (bukan `ConfigService` NestJS) — `seed.ts` jalan di luar Nest DI container dan perlu bisa bikin instance langsung dari `process.env`; `AudioModule` nyediain wiring NestJS-nya lewat `useFactory`. `TtsClient` abstract class jadi token DI (pola sama `REDIS_CLIENT`) supaya `AudioService` bisa dites dengan implementasi palsu tanpa kredensial sungguhan.

**Azure Cognitive Speech** dipanggil langsung lewat REST API (`fetch` ke `https://{region}.tts.speech.microsoft.com/cognitiveservices/v1`, body SSML) — BUKAN `microsoft-cognitiveservices-speech-sdk` (itu untuk skenario streaming, kebutuhan di sini cuma satu request sinkron). **Provider ini masih rekomendasi plan, belum final** (lihat "Yang Masih Perlu Dikonfirmasi").

**Yang SUDAH diverifikasi** (skrip manual sekali-pakai, dihapus setelah dipakai): pipeline caching PENUH terhadap S3 sungguhan — LocalStack (`localstack/localstack:3`), BUKAN MinIO (MinIO Corp membatasi pull `minio/minio:latest` dari Docker Hub, persisten di sandbox ini, sudah dicoba beberapa kali + coba `quay.io/minio/minio` yang malah diblok kebijakan jaringan sandbox — lihat catatan lingkungan di bagian "Status Implementasi"; LocalStack API-compatible sama seperti MinIO jadi tetap membuktikan kode S3-nya benar). Terverifikasi: cache miss → generate+upload+simpan baris baru; cache hit kedua kali → TTS provider TIDAK terpanggil lagi (dicek pakai counter), url sama persis; byte yang tersimpan di S3 diverifikasi LANGSUNG (bukan cuma "SDK call tidak error") cocok dengan yang di-upload. `ContentService`/`seed.ts` diregresi-cek jalan normal (seed tetap sukses dengan output sama seperti sebelumnya, `GET /lessons/:id` tetap merespons benar) tanpa kredensial Azure/S3 nyata.

**Yang BELUM diverifikasi**: panggilan Azure Cognitive Speech API itu sendiri — TIDAK ADA kredensial (`AZURE_SPEECH_KEY`/`REGION`) di lingkungan mana pun sejauh ini. `AzureTtsClient` ditulis sesuai dokumentasi REST API Azure tapi belum pernah benar-benar dipanggil. `seed.ts` mendeteksi kredensial kosong dan SKIP seluruh langkah audio dengan satu peringatan jelas (bukan gagal/crash) — jadi seed tetap 100% jalan seperti sebelumnya di lingkungan tanpa kredensial ini, cuma audio-nya kosong.

## 6d. Scenarios/Dictionary/Flashcards — SELESAI (Milestone 9 lanjutan)

Tiga modul independen, semua di belakang `JwtStudentAuthGuard`, melengkapi Milestone 9 (tabel modul bagian 3).

**`packages/domain/src/scenario/`** (BUKAN port -- tidak ada padanan di app lama, lihat catatan riset di atas soal `server/ai_tutor` vs modul ini: `TutorScenario` nanti [Milestone 11] itu system-prompt LLM bebas, `Scenario` Prisma/`ScenarioSession` di sini itu template percakapan terstruktur dengan jawaban benar/salah tetap, dua hal yang berbeda). `types.ts` mendefinisikan skema zod CONV-02 (`ScenarioContent`, `ScenarioLine` = union `NarrationLine`/`ChoiceLine` -- pakai `z.union` bukan `z.discriminatedUnion` karena `NarrationLine` tidak punya field pembeda eksplisit seperti `type`). Dua keputusan desain di luar contoh literal PRD: (1) `estimated_minutes` ditambahkan ke skema -- dibutuhkan untuk tampilan katalog CONV-01 dan skor time-bonus (lihat di bawah); (2) `vocab: string[]` di `ScenarioContent` menyimpan ID `Vocab` (referensi), BUKAN data kata inline -- supaya CONV-05 ("tambah ke flashcard dari skenario") bisa langsung pakai `ReviewItem`/`SrsService` yang sudah ada tanpa duplikasi data kata.

**`ScenarioSession`** (`scenarioSession.ts`) SENGAJA didesain beda dari `LessonSession` di satu hal penting: jawaban salah TIDAK diantre ulang ke akhir (requeue-to-end, pola `LessonSession`) -- baris dialog itu linear/naratif, requeue akan membuat murid lihat balasan lawan bicara atas baris berikutnya sebelum baris mereka sendiri selesai, merusak alur percakapan. Jadi jawaban salah membuat sesi **tetap di baris yang sama (retry-in-place)**. Konsekuensi lain dari desain ini: opsi jawaban TIDAK PERNAH diacak (beda dari opsi `choose` lesson yang di-shuffle `ExerciseFactory`), jadi `currentIndex` (posisi baris) aman dipakai sebagai pengecekan integritas replay di server -- tidak perlu pola value-based seperti `LessonSession`/`refId`.

- **`TEST_MODE_MAX_MISTAKES = 3`** (CONV-04 AC: "3x kesempatan salah total") -- **PROPOSAL**, PRD tidak memberi alternatif angka untuk dibandingkan (beda dari star→XP yang setidaknya punya rentang literal di PRD). Mode test: retry tetap diizinkan tapi tiap salah memotong kesempatan bersama; begitu melebihi budget, sesi berakhir **seketika** (`isFinished=true` di tengah `submitChoice()`, tidak menunggu baris sisa). Mode practice: retry tanpa batas, tidak pernah gagal.
- **Skor formula (`scenarios.service.ts`)** -- **PROPOSAL**, PRD tidak beri angka: `timeBonus = durasi<=estimasi ? 10 : durasi<=estimasi*1.5 ? 5 : 0`, `score = min(100, accuracyPercent + timeBonus)`, `passed = accuracyPercent>=80 && !failed`.
- **XP skenario cuma diberikan sekali** -- sama seperti kebijakan anti-farming lesson (bagian "Yang Masih Perlu Dikonfirmasi" di bawah): hanya mode TEST, dan hanya kalau ini percobaan TEST **pertama** untuk skenario itu (dihitung dari `ScenarioAttempt` yang sudah ada sebelum baris baru dibuat) -- percobaan TEST berikutnya (atau mode PRACTICE kapan pun) tidak menghasilkan XP baru, tapi `ScenarioAttempt` tetap disimpan untuk KEDUANYA (praktik maupun tes) supaya riwayat lengkap. `XpService.scenarioXp` = 20 (properti angka tetap, bukan fungsi seperti `lessonXp(stars)` -- skenario tidak punya konsep bintang).
- **Audio semua baris skenario pakai voice `'female'` hardcode** -- belum ada konsep "suara per karakter" di skema `ScenarioContent`; jadi gap yang diketahui untuk Milestone 11 (`TutorModule` sudah punya `voice`/`voice_instructions` per karakter di rencana port, lihat bagian 6) kalau nanti mau dipakai juga di sini.
- `ScenariosService.detail()`/replay attempt keduanya me-**re-validasi `Scenario.payload` lewat `scenarioContentSchema.safeParse()` di SETIAP BACA**, BUKAN cuma di seed time seperti konten lesson (bagian 5/`ContentModule`) -- beda desain SENGAJA: konten lesson didekomposisi jadi baris relasional (`Vocab`/`Sentence`/`Exercise`) yang masing-masing sudah tervalidasi satu kali saat upsert, sementara `Scenario.payload` itu SATU blob JSON mentah (`Json` column Prisma), jadi tidak ada jaminan struktural dari skema DB relasional -- validasi ulang tiap baca murah (satu skenario kecil) dan menangkap payload yang mungkin diedit manual/corrupt di masa depan (mis. lewat Prisma Studio atau editor konten admin Fase 2).
- **Bug nyata ketemu+diperbaiki SAAT verifikasi manual end-to-end** (bukan cuma ditulis lalu diasumsikan benar, persis pola bagian 6c): `ScenarioSession.next()` melempar `Error: sesi sudah selesai` (500 di server) kalau dipanggil PERSIS setelah `submitChoice()` yang melebihi budget mode test -- `submitChoice()` bisa men-set `this.failed=true` (membuat `isFinished` true) DI TENGAH pemanggilannya sendiri, tapi replay loop `ScenariosService.submitAttempt` mengikuti pola normal submitChoice()→next() tanpa cek `isFinished` di antaranya (sama seperti caller normal manapun seharusnya boleh), dan `next()` versi lama langsung baca `this.current` yang melempar begitu selesai. Ketahuan lewat skrip verifikasi e2e sungguhan terhadap Postgres+Redis nyata (unit test yang ada sebelumnya tidak pernah memanggil `next()` persis di titik itu). **Diperbaiki**: `next()` sekarang `if (this.isFinished) return;` di baris pertama (no-op, bukan melempar) -- ditambahkan test regresi eksplisit (`scenarioSession.test.ts`, test "melebihi TEST_MODE_MAX_MISTAKES...") yang memanggil `next()` persis di urutan yang tadinya crash.
- **Baru 1 dari 10 skenario MVP PRD yang diauthoring** (`perkenalan` / 自己紹介, N5, 5 baris) -- sama seperti Hiragana-only-content (bagian 5), authoring 9 skenario sisa adalah kerja konten terpisah (product owner/pengajar), bukan kerja kode. **`DictionaryModule`** (SUP-01): `GET /dictionary?q=` mencari `Vocab` lewat `OR` di kolom `jp`/`reading`/`romaji`/`meaningId` (`contains`, `mode:"insensitive"`, take 50), audio ter-resolve lewat `loadAudioUrlsByHash` yang sama dipakai modul lain. Data kamus sungguhan (target PRD "min. 1500 entri N5") **belum diauthoring** -- yang ada sekarang cuma 3 entri baru yang dibuat untuk skenario `perkenalan` (`voc_hajimemashite`/`voc_onamae`/`voc_yoroshiku`) + 104 vocab Hiragana lama (bagian 5), jauh dari target. Backend sekarang sudah lengkap (auth, lessons, gamification, audio, admin, scenarios, dictionary, flashcards) untuk digantungi — jauh lebih siap dibanding titik sebelumnya, kemungkinan urutan paling masuk akal berikutnya supaya ada sesuatu yang benar-benar bisa dipakai di browser (walking-skeleton Milestone 12).
