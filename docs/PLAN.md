## Keputusan Lintas-Sektor

- **Grading server-authoritative, UX client-optimistic.** `GET /lessons/:id` tetap kirim data exercise lengkap (opsi + kunci jawaban) supaya `exerciseFactory.ts`/`lessonSession.ts` bisa dipakai ulang di browser untuk feedback instan per-soal. Tapi `POST /lessons/:id/attempts` **menghitung ulang skor di server** pakai fungsi `packages/domain` yang SAMA — skor yang disimpan/dapat XP selalu hasil hitungan server, bukan self-report client (perlu karena sekarang ada leaderboard antar-murid, tidak seperti app lama yang single-user/local-trusted).
- **`unlockRules.ts` ditegakkan di server**, bukan cuma di client — `LessonsModule` cek status unlock terhadap `UserLessonProgress` sebelum menerima attempt.
- **`packages/domain` tetap bebas dari Prisma** — fungsi murni, tidak tahu soal database; service di `apps/api` yang jadi lem ke Prisma.
- **Angka XP: PRD menang, tapi mekanismenya di-porting.** Formula lama pakai `10 + 1×correctFirstTry + 5×speakHighCount` + level curve `100×n`. PRD v4.0 (GAM-01/03) minta angka beda: lesson +10–30, checkpoint +50, percakapan +20, kuis harian +10, level curve `1000×n`. Sudah diimplementasi di `packages/domain/src/gamification/xpService.ts` dengan mapping bintang→XP ★=10/★★=20/★★★=30 — **PROPOSAL, perlu dikonfirmasi ke product owner** (PRD kasih rentang & tingkat bintang terpisah, tidak pernah eksplisit memetakan keduanya). `starsForScore(accuracyPercent)` juga sudah ada di file yang sama (ambang LP-03: 80-89=1, 90-99=2, 100=3) — tapi **belum ada yang MEMANGGIL fungsi ini** dari alur completion lesson sungguhan; itu tugas `LessonsModule` (Milestone 7, belum dikerjakan).
- **XP jangan dobel fungsi.** GAM-03 (level/leaderboard) butuh XP monoton naik; GAM-02 (beli streak-freeze pakai 50 XP) butuh XP jadi mata uang yang bisa dibelanjakan. Kalau keduanya pakai ledger yang sama, beli freeze bisa bikin rank turun — kemungkinan tidak diinginkan. **Keputusan:** `XpEvent` tetap ledger append-only selalu positif (sumber kebenaran level+leaderboard); pembelian freeze jadi counter terpisah, bukan `XpEvent` negatif.
- **Auth student vs admin benar-benar terpisah** — signing secret, audience, dan tabel refresh-token yang beda, bukan cuma route beda — supaya token murid yang bocor tidak bisa dipakai sebagai token admin. Sudah diimplementasi (`AuthModule` vs `AdminAuthModule`).

## 1. Struktur Monorepo

**pnpm workspaces + Turborepo.** Nx terlalu berat untuk graf sekecil ini (2 frontend Vite + 1 backend Nest + beberapa shared package); plain workspaces tanpa task runner berarti urutan build/caching harus diatur manual begitu CI masuk. Turborepo pas di tengah: orkestrasi `turbo run build|test|lint` lintas workspace + caching, cukup satu file config, gampang dilepas kalau suatu saat tidak perlu. pnpm dipilih karena `node_modules` yang strict (menangkap impor silang antar-paket yang tidak sengaja — penting supaya `packages/domain` tetap benar-benar decoupled).

```
<repo>/
├── apps/
│   ├── student/          # React + Vite + TS + Tailwind + shadcn/ui, PWA (vite-plugin-pwa)
│   ├── admin/             # React + Vite + TS + Tailwind + shadcn/ui (tanpa PWA)
│   └── api/               # NestJS
│       ├── prisma/{schema.prisma, seed.ts, seed-data/raw/unit_hiragana.json}
│       └── src/
├── packages/
│   ├── domain/            # logic murni hasil porting — TIDAK impor Prisma. Build step tsc->CommonJS
│   │                       # (BUKAN "TS-source-only" seperti draft awal plan ini bilang -- lihat
│   │                       # catatan "koreksi" di bagian bawah plan ini, penting dibaca)
│   ├── ui/                # primitif shadcn/ui + preset Tailwind + design token (shell doang, bukan fitur)
│   └── config/            # tsconfig/eslint/prettier/tailwind preset dasar
├── turbo.json
├── pnpm-workspace.yaml
├── docker-compose.yml      # lokal (dev): postgres + redis + penyimpanan S3 (SeaweedFS; MinIO tak bisa ditarik lagi)

└── .github/workflows/ci.yml
```

Tidak ada `packages/api-types` manual — lihat poin 7 (OpenAPI codegen) supaya tidak ada drift tipe frontend vs backend.

**KOREKSI PENTING dari draft awal plan ini:** draft ini semula bilang "tiap package workspace TS-source-only, tanpa build dist terpisah." Itu SALAH dan sudah diperbaiki saat implementasi: `apps/api` (NestJS) di-compile jadi JS lalu dijalankan `node dist/main.js` di produksi/Docker — proses `node` murni itu TIDAK BISA `require()` file `.ts` mentah. Jadi `packages/domain` (dan `packages/ui`) SEKARANG punya build step `tsc` sungguhan (`"build": "tsc"`, `main`/`types` menunjuk ke `dist/`), bukan menunjuk ke `src/`. `packages/domain` di-compile ke **CommonJS** (harus cocok dengan `apps/api` yang juga CommonJS — sempat salah coba ESM dulu, ketahuan lewat smoke test `require()` sungguhan yang gagal, lihat commit `458971b`). `packages/ui` boleh tetap ESM (`"type": "module"`) karena cuma dikonsumsi Vite (bundling, bukan `node require()` langsung).

## 4. Auth (SUDAH DIIMPLEMENTASI — `apps/api/src/auth/`, `src/admin-auth/`, `src/users/`)

- **Token undangan**: random opaque (`crypto.randomBytes(32).toString('base64url')`), yang disimpan cuma `sha256(token)` (`src/common/opaque-token.util.ts`) — bukan JWT (JWT tidak bisa di-revoke tanpa blocklist, padahal ADM-12 butuh resend/revoke).
- **Registrasi**: validasi token → hash password `argon2id` → `User` dibuat dengan `classId`/`email` dari `Invitation` yang tervalidasi di server (BUKAN dari body request) → invitation jadi `ACCEPTED` → langsung terbitkan access+refresh JWT (auto-login).
- **JWT**: `@nestjs/jwt`+`@nestjs/passport`+`passport-jwt`; access 1 jam, refresh 14 hari, secret terpisah student (`JWT_STUDENT_SECRET`) vs admin (`JWT_ADMIN_SECRET`). Rotasi refresh dengan deteksi-reuse: token yang sudah di-revoke tapi dipakai lagi → revoke seluruh chain, paksa re-login. Payload JWT `sub` juga dicocokkan dengan `userId`/`adminUserId` hasil lookup DB (pertahanan berlapis).
- **Rate limit/lockout**: lockout 5x-gagal→15 menit per-akun lewat Redis (`login_fail:{email}`/`login_lock:{email}`), dengan email BAKU (huruf kecil) sebagai kunci -- ejaan lain tidak melewati/memecah lockout (bagian 6f). `/auth/forgot` dibatasi per IP dan per email (bagian 6f).
- **Lupa password**: `/auth/forgot` selalu balas 200 (no user enumeration). `/auth/reset` revoke SEMUA refresh token user itu, DAN mencabut kunci login akun itu (`login_lock`/`login_fail`, lihat bagian 7i temuan 1): tautan reset membuktikan pemilik menguasai emailnya, dan tanpa ini murid yang terkunci tetap ditolak sampai 15 menit walau sudah mengganti password.
- ~~BELUM ADA YANG BISA DITES END-TO-END SUNGGUHAN~~ **SUDAH** — diverifikasi lewat REST client sungguhan terhadap Postgres+Redis di Milestone 5 (lihat "Verifikasi"), dan lewat BROWSER sungguhan untuk jalur masuk murid (undangan → registrasi → onboarding, lupa/reset password, kunci login) di bagian 7i.

## 5. Migrasi Konten Hiragana — SELESAI (Milestone 6)

`apps/api/prisma/seed.ts` sudah jalan sungguhan (bukan stub lagi), idempotent (dites re-run 2x, row count sama). Yang ternyata beda dari rencana awal:

1. `unit_hiragana.json` disalin ke `apps/api/prisma/seed-data/raw/` seperti rencana.
2. Skema zod `packages/domain`'s `unitSchema` jadi gerbang validasi SEBELUM upsert, persis rencana.
3. **Skema Prisma ternyata kurang lengkap untuk menampung konten** (baru ketahuan saat benar-benar coba migrasi data, bukan pas nulis draft skema Milestone 3) — dua perbaikan skema (migrasi Prisma baru, bukan cuma dokumentasi):

Field: `surface/kana/romaji/meaning/words(json)/assembleTokens(json?)/voice`, unit-scoped.
   - **`Unit.description`/`Unit.type`/`Unit.grammarNotes`** ditambahkan (draft awal cuma punya `title`/`order`) — dibutuhkan domain `Unit` type.
   - **`Vocab.meaningId` diubah dari wajib jadi nullable** — 104/104 vocab Hiragana TIDAK punya `meaning_id` (karakter fonetik murni, bukan kosakata berarti, mis. あ) di data sungguhan; draft skema salah asumsi field ini selalu terisi.
4. Upsert idempotent by natural key (id dari JSON dipertahankan, BUKAN cuid baru): `Level` HIRAGANA → `Unit` → `Vocab` (104) → `Sentence` (56) → `Lesson` (7) → `Exercise` (CHOOSE/ASSEMBLE reshape langsung, id sintetis `${lessonId}_${order}`; tipe `speak` **tidak dimigrasikan sebagai Exercise** — 56 exercise speak di-skip, datanya tetap ada lewat `Vocab`/`Sentence` yang sudah di-upsert terpisah) → 7 badge statis (unit Hiragana bertipe `kana`, bukan `conversation`, jadi TIDAK dapat badge dinamis per-unit — sesuai `BadgeCatalog.all` yang cuma menghasilkan badge untuk unit `conversation`).
5. Diverifikasi via query langsung (bukan cuma Prisma Studio manual): `Vocab`=104, `Sentence`=56, `Lesson`=7, `Exercise`=128 (104 choose + 24 assemble), `Badge`=7. Re-run kedua menghasilkan angka SAMA (idempotent, tidak dobel).
6. Katakana/Dasar/N5/N4 masih di luar fase ini — authoring konten kerjaan terpisah (pemilik produk + pengajar), pakai pipeline seed yang sama (`toDomainUnit`/`unitSchema` sudah generik, tidak Hiragana-specific).

**Keputusan yang MENAMBAH/MENGUBAH rencana awal** (bukan port murni — jangan dianggap "perilaku versi lama"):
1. **Kuota atomik (skrip Lua di Redis)**: cek-lalu-naikkan dalam satu langkah — counter tidak pernah melewati limit. Membetulkan race check-then-act versi lama.
2. **Jatah DIKEMBALIKAN kalau panggilan LLM gagal** (`refund`, memakai `now` yang SAMA dengan `consume` supaya mengenai counter hari yang benar walau panggilan melewati tengah malam). Spesifikasi lama tidak mencatat perilaku ini — keputusan baru, murid tidak rugi karena gangguan di sisi kita/provider.
3. **Cek kredensial SEBELUM kuota** (dari catatan lama, dites: 6 request ke server tanpa API key → semuanya 503, tidak pernah 429, key Redis tidak pernah dibuat).
4. **Pengaman biaya**: riwayat maks 40 giliran × 500 karakter, kosakata maks 30 × 40 karakter, teks `speak` maks 500 karakter, audio maks 10 MiB; `transcribe`/`speak` (TIDAK punya kuota harian — kuota lama cuma untuk balasan) dibatasi 20 request/menit/route lewat `@Throttle`; timeout SDK 45 detik + `maxRetries: 1` (bawaan SDK 10 menit + 2 retry terlalu lama untuk endpoint interaktif).
5. **Privasi**: `store:false` di Responses API — isi percakapan murid tidak disimpan di sisi OpenAI (server stateless; riwayat dibawa client di tiap request). Detail error provider cuma masuk log server (tanpa isi percakapan) dan TIDAK PERNAH ke client (dites: kunci API/pesan provider tidak bocor di body 502/503).
6. **Hardening prompt**: pemisah baris di dalam teks murid/kosakata dilipat jadi spasi, supaya murid tidak bisa menyelipkan baris `assistant: ...` palsu ke riwayat atau membuka bagian instruksi baru lewat kosakata.
7. **Batas biaya ditegakkan oleh `ValidationPipe`** -- di Milestone 11 dipasang LOKAL di `TutorController` karena API belum punya yang global; sejak slice bagian 6e tutor memakai pipe GLOBAL (pipe lokal dihapus, opsi dibagi lewat `common/validation.ts`) dan e2e tutor (96 + 13 + 7) lulus ulang tanpa perubahan.
8. **`hashAudioKey(textJp, voice)` dilebarkan** dari `'female'|'male'` jadi `string` bebas — digest untuk input lama TIDAK berubah (dites dengan digest sungguhan yang dipatok). Inilah "perluasan ke hash(text+voiceId)" yang disiapkan di 6b, tanpa migrasi skema.
9. **Perbaikan kecil di luar scope, ketemu saat regenerasi OpenAPI**: `RedisModule` tidak pernah menutup koneksi ioredis-nya, jadi proses apa pun yang memanggil `app.close()` (mis. `pnpm run generate-openapi`) tidak pernah selesai sendiri. Sekarang `onModuleDestroy` → `redis.quit()`; `generate-openapi` selesai sendiri ~8 detik dengan exit 0 dan hasilnya byte-identik antar run.

## 6b. Pipeline Audio TTS (`AudioModule`) — SELESAI (Milestone 8)

Implementasi di `apps/api/src/audio/`: `hashAudioKey(textJp, voice)` (sha256 dari `text|voice`, BUKAN cuma `sha256(text)` — sudah `hash(text+voiceId)` sejak awal, persis catatan di bagian 6 di atas soal `POST /tutor/speak`; `voice` awalnya cuma `'female'|'male'`; **sudah diperluas di Milestone 11** jadi `string` bebas untuk voice-per-karakter TutorModule, tanpa migrasi skema -- lihat bagian 6) → `AudioService.resolveAudioUrl(textJp, voice)`: cek `AudioAsset` by hash, cache hit → balikin `s3Url` tersimpan (TIDAK panggil TTS provider lagi — diverifikasi), cache miss → generate (`TtsClient`) → upload (`ObjectStorageService`, S3-compatible) → `upsert` baris baru.

**Kapan dipanggil — SAAT SEED, bukan saat request.** NFR eksplisit minta API p95 < 300ms; generate TTS sinkron di dalam `GET /lessons/:id` akan melanggar itu telak (TTS + upload S3 bisa makan waktu detik-an). Jadi `seed.ts` memanggil `resolveAudioUrl` untuk tiap vocab/sentence SEKALI di waktu migrasi konten (best-effort, lihat di bawah); `ContentService.loadUnit` di request-time cuma melakukan SATU query bulk `AudioAsset.findMany({textHash: {in: [...]}})` (murah, baca-saja) lalu isi field `audio` domain Vocab/Sentence dari situ — kosong (`""`, placeholder jujur bukan url palsu) untuk teks yang belum pernah digenerate. Pola cache yang sama SEKARANG dipakai TutorModule (Milestone 11, lewat `AudioService.resolveAudioUrlWith`) untuk `/tutor/speak`, TAPI di sana panggilannya on-demand/interaktif (balasan AI dinamis, tidak bisa di-pre-generate) — beda karakteristik dari audio konten lesson yang sudah diketahui sebelum murid membuka lesson-nya.

**Seam TtsClient/ObjectStorageService** (`tts-client.ts`, `azure-tts.client.ts`, `object-storage.service.ts`) sengaja nerima NILAI MENTAH di constructor (bukan `ConfigService` NestJS) — `seed.ts` jalan di luar Nest DI container dan perlu bisa bikin instance langsung dari `process.env`; `AudioModule` nyediain wiring NestJS-nya lewat `useFactory`. `TtsClient` abstract class jadi token DI (pola sama `REDIS_CLIENT`) supaya `AudioService` bisa dites dengan implementasi palsu tanpa kredensial sungguhan.

**Azure Cognitive Speech** dipanggil langsung lewat REST API (`fetch` ke `https://{region}.tts.speech.microsoft.com/cognitiveservices/v1`, body SSML) — BUKAN `microsoft-cognitiveservices-speech-sdk` (itu untuk skenario streaming, kebutuhan di sini cuma satu request sinkron). **Provider ini masih rekomendasi plan, belum final** (lihat "Yang Masih Perlu Dikonfirmasi").

**Yang SUDAH diverifikasi** (skrip manual sekali-pakai, dihapus setelah dipakai): pipeline caching PENUH terhadap S3 sungguhan — LocalStack (`localstack/localstack:3`), BUKAN MinIO (MinIO Corp membatasi pull `minio/minio:latest` dari Docker Hub, persisten di sandbox ini, sudah dicoba beberapa kali + coba `quay.io/minio/minio` yang malah diblok kebijakan jaringan sandbox — lihat catatan lingkungan di bagian "Status Implementasi"; LocalStack API-compatible sama seperti MinIO jadi tetap membuktikan kode S3-nya benar). Terverifikasi: cache miss → generate+upload+simpan baris baru; cache hit kedua kali → TTS provider TIDAK terpanggil lagi (dicek pakai counter), url sama persis; byte yang tersimpan di S3 diverifikasi LANGSUNG (bukan cuma "SDK call tidak error") cocok dengan yang di-upload. `ContentService`/`seed.ts` diregresi-cek jalan normal (seed tetap sukses dengan output sama seperti sebelumnya, `GET /lessons/:id` tetap merespons benar) tanpa kredensial Azure/S3 nyata.

**Yang BELUM diverifikasi**: panggilan Azure Cognitive Speech API itu sendiri — TIDAK ADA kredensial (`AZURE_SPEECH_KEY`/`REGION`) di lingkungan mana pun sejauh ini. `AzureTtsClient` ditulis sesuai dokumentasi REST API Azure tapi belum pernah benar-benar dipanggil. `seed.ts` mendeteksi kredensial kosong dan SKIP seluruh langkah audio dengan satu peringatan jelas (bukan gagal/crash) — jadi seed tetap 100% jalan seperti sebelumnya di lingkungan tanpa kredensial ini, cuma audio-nya kosong.

## 6e. Validasi DTO (`class-validator`) — DIPERBAIKI (sebelumnya TIDAK aktif di seluruh API, plus celah mass assignment di `PATCH /me`)

**Temuan** (Milestone 11, dibuktikan sungguhan terhadap API yang berjalan SEBELUM diperbaiki — bukan cuma dibaca dari kode): `ValidationPipe` tidak pernah didaftarkan — tidak ada `useGlobalPipes`, `APP_PIPE`, maupun `@UsePipes`. Tanpa pipe, NestJS tidak menjalankan dekorator `class-validator` sama sekali; DTO cuma dipakai plugin Swagger sebagai sumber skema OpenAPI, itu sebabnya spesifikasi tampak benar dan tidak ada yang curiga. Body request masuk MENTAH ke service.

**Bukti sebelum perbaikan** (semua data uji sudah dipulihkan/dihapus setelahnya):

| Request | Seharusnya (menurut DTO) | Sebenarnya |
|---|---|---|
| `PATCH /me {"dailyXpGoal":999}` (`@IsIn([10,30,50])`) | 400 | **200, tersimpan 999** |
| `PATCH /me {"name":""}` (`@MinLength(1)`) | 400 | **200, nama kosong tersimpan** |
| `PATCH /me {"dailyXpGoal":"banyak"}` | 400 | **500** (error Prisma) |
| `POST /auth/register {name:"", password:"a"}` (AC AUTH-02: min. 8 karakter, huruf+angka) | 400 | **201 — akun terbuat dengan password 1 karakter; login dengan "a" berhasil** |
| `POST /admin/invitations` tanpa field `name` | 400 | **500** (`Argument name is missing`, error Prisma) |
| **`PATCH /me {"classId":"<kelas lain>"}`** | 400 | **200 — murid memindahkan DIRINYA SENDIRI ke kelas lain** (fitur khusus admin, ADM-21) |
| **`PATCH /me {"email":"penyerang@…"}`** | 400 | **200 — email diganti tanpa verifikasi** (bersama `/auth/forgot` = jalur pengambilalihan akun permanen bagi siapa pun yang sempat memegang access token curian, walau umurnya cuma 1 jam) |
| **`PATCH /me {"lastActiveAt":"2001-…"}`** | 400 | **200 — kolom internal tertulis** |

Dua baris terakhir ternyata BUKAN sekadar "validasi tidak jalan" melainkan **mass assignment**: `UsersService.update` memakai `data: dto`, jadi body mentah langsung ke `prisma.user.update` dan murid bisa menulis SETIAP kolom `User`-nya (`classId`, `email`, `status`, `passwordHash`, ...). Dicek: itu satu-satunya tempat body mentah masuk ke tulis DB; service lain (`admin-students`, `admin-classes`, dst.) memilih field satu per satu. Juga `AuthService.register`/`resetPassword` langsung meng-hash apa pun yang diterima — tidak ada pengecekan manual sebagai cadangan, jadi kebijakan password AUTH-02 memang tidak berlaku sama sekali.

**Perbaikan (berlapis — tidak bergantung pada satu mekanisme)**:
1. **`ValidationPipe` GLOBAL** lewat `APP_PIPE` di `AppModule` (opsi di `common/validation.ts`): `whitelist` + `forbidNonWhitelisted` + `transform`. Field tak dikenal → 400 (bukan diteruskan diam-diam), nilai melanggar dekorator → 400, handler menerima instance DTO. Guard tetap berjalan SEBELUM pipe (anonim/salah-peran → 401, bukan 400, jadi tidak ada bocoran validasi ke pihak tak berhak).
2. **`UsersService.update` memilih tiga field** (`name`, `avatarUrl`, `dailyXpGoal`) satu per satu — penulisan ke DB TIDAK boleh bergantung pada pipe; kalau pipe hilang lagi, hanya tiga field itu yang lolos. Dites dengan mensimulasikan pipe yang hilang.
3. **`@Trim()`** (`common/trim.decorator.ts`) di semua field `name` (register, kelas, undangan, profil): `@MinLength(1)` saja meloloskan "   ". Sengaja TIDAK untuk password (spasi sah) atau email (normalisasi email = perilaku lama, tidak diubah).
4. **Pipe lokal `TutorController` (Milestone 11) dihapus** — tutor memakai pipe global; opsi dibagi lewat `common/validation.ts`.
5. **`ProfilePage` memangkas nama dan menolak nama kosong di klien** dengan pesan jelas — `required` bawaan browser meloloskan "   ", padahal server kini menolaknya (tanpa ini murid mendapat "Gagal menyimpan" dari request yang pasti 400).

**Audit sebelum dinyalakan** (supaya tidak memecah UI): semua properti DTO sudah berdekorator (jadi `whitelist` tidak membuang field yang dibutuhkan); payload SETIAP pemanggil di `apps/student`/`apps/admin` dibaca dan ternyata sudah persis bentuk DTO — event lesson `{ref, kind, choiceText|tokens}`, event percakapan `{lineIndex, optionIndex}` dengan `durationSec` dibulatkan, filter dikirim `|| undefined` (bukan string kosong), `correct` boolean sungguhan, dst.; data di DB tidak melanggar aturan baru (email valid, `dailyXpGoal` ∈ {10,30,50}, tak ada nama kosong); service sudah punya pengecekan silang sendiri (mis. `choiceText` wajib untuk tipe choose → 400).

**Penjaga supaya tidak hilang lagi** — semuanya berjalan tanpa Redis/Postgres/`.env` (dites pada salinan bersih):
- `common/validation.test.ts`: `AppModule` HARUS mendaftarkan `APP_PIPE` bertipe `ValidationPipe`, yang menolak nilai buruk dan field tak dikenal. Dibuktikan gagal keras (dengan pesan yang menunjuk bagian ini) kalau providernya dihapus.
- `common/controller-input-guard.test.ts`: audit STATIS lewat compiler TypeScript atas SEMUA controller — tiap `@Body()`/`@Query()` harus bertipe class DTO (bukan interface, tipe literal, `any`, atau `@Body("x")` yang meloloskan input TANPA validasi apa pun, diam-diam), seluruh propertinya berdekorator, dan properti bersarang wajib `@ValidateNested` + `@Type`. Penjaga ini punya 13 self-test sendiri dan dibuktikan lewat mutasi pada controller/DTO sungguhan.
- `common/dto-contract.test.ts` (110 kasus): kontrak tiap DTO — payload sah persis seperti yang dikirim frontend + semua kasus tolak (kebijakan password AUTH-02, mass assignment, enum, bilangan bulat, `score`/`correct` tak bisa diselipkan client, dst.).
- `users/users.service.test.ts`: service tidak menulis field di luar tiga yang boleh walau menerima body mentah.

**Verifikasi terhadap sistem nyata**:
- API `nest build` asli + Postgres + Redis, 106 pemeriksaan: semua bukti di tabel kini 400 DAN baris DB tidak berubah; register + lupa/reset password NYATA lewat undangan asli (password lemah ditolak dan tidak menghabiskan token, yang sah diterima; `classId`/`email` tetap dari undangan, bukan body); kontrol positif untuk login/refresh/CRUD admin/attempt/kamus/profil; guard-sebelum-pipe; body bukan-JSON/`null`/array → 400 (bukan 500); upload CSV multipart tetap jalan. Regresi e2e tutor (96 + 13 + 7) lulus ulang tanpa perubahan setelah pipe lokal diganti global.
- **Browser sungguhan (Playwright)**: 33 asersi atas 89 panggilan API dari alur UI nyata — lesson (event benar+salah yang diulang, dua tipe), percakapan latihan/tes/tes-gagal, flashcard, kamus, profil, admin kelas/undangan/filter/murid — **nol request sah tertolak** (satu-satunya 400 = nama kelas spasi-saja yang memang diuji); plus refresh token dari browser untuk kedua app (14 asersi, deteksi reuse tetap tegak).
- `openapi.json` dan `packages/api-client` tidak berubah (byte-identik); `pnpm turbo run typecheck lint test` hijau.

**Perilaku baru yang perlu diketahui**:
- Field tak dikenal di body/query → 400. Frontend kita tidak mengirimnya (diaudit + diregresi). Kalau kelak ada klien lama yang harus dilonggarkan: `forbidNonWhitelisted: false` di `common/validation.ts` — field tetap DIBUANG, cuma tak lagi 400.
- Bentuk error = default NestJS `{statusCode: 400, message: string[], error: "Bad Request"}`. Pesan bawaan class-validator berbahasa INGGRIS (kecuali kebijakan password yang sudah Indonesia). UI sekarang tidak menampilkan pesan server (memakai teks tetap sendiri); halaman auth publik yang akan dibangun sebaiknya memetakan pesan/field ke Indonesia.
- Login/forgot dengan email berbentuk salah → 400 (dulu 401/200) dan tidak menyentuh penghitung lockout.
- Spesifikasi OpenAPI tidak mendokumentasikan respons 400, dan plugin Swagger tidak menerjemahkan `@ArrayMaxSize` (batas 40 giliran/30 kosakata tutor cuma tegak di runtime).

**Yang BELUM / catatan jujur**:
- Akun yang SUDAH terlanjur dibuat dengan password lemah, atau data hasil mass assignment (`email`/`classId`/`status`), TIDAK diperbaiki otomatis — password cuma tersimpan sebagai hash sehingga tidak bisa diaudit. Di DB dev cuma ada akun uji (dicek: semua nilainya sah). Kalau kelak ada pengguna sungguhan yang dibuat sebelum perbaikan ini: audit `users` (email/class_id/status) dan minta reset password.
- `@IsUrl()` pada `avatarUrl` (default `require_tld`) menolak URL tanpa TLD seperti `http://localhost:9000/…`; tak ada UI/endpoint yang memakainya sekarang — sesuaikan saat fitur avatar dibangun.
- `PATCH /me` sengaja tidak bisa mengubah `email`; kalau produk butuh itu, harus jadi alur terverifikasi tersendiri (bukan menambah field di DTO ini).

## 6f. Pengerasan Auth — email huruf kecil, batas `/auth/forgot`, `TRUST_PROXY` — SELESAI

Butir "pengerasan auth sebelum go-live" dari prioritas (ditemukan di bagian 7i) dikerjakan atas persetujuan user. Tiga hal, plus satu perbaikan UI kecil yang menyertainya:

**1. Email disimpan, dicari, dan dipakai sebagai kunci Redis dalam HURUF KECIL.** Masalahnya nyata. Dibuktikan lewat API hidup sebelum diperbaiki: `login` dengan `E2E-Student@Example.com` (password benar) → 401, dan undangan menyimpan email persis seperti diketik admin. Menurut pembacaan kode (belum diprobe terpisah): lupa-password tidak menemukan akun bila kapitalisasinya beda sehingga tautan reset tidak pernah terkirim, dan lockout login (5x gagal) bisa dilewati dengan mengganti kapitalisasi karena kuncinya `login_lock:{email-apa-adanya}`. Perbaikan berlapis (pola yang sama dengan bagian 6e):
- `common/email.util.ts` `normalizeEmail` (trim + `toLowerCase()`, sengaja BUKAN `toLocaleLowerCase()` dan tanpa kanonikalisasi ala Gmail: titik dan `+tag` adalah bagian alamat yang sah) dan dekorator `@NormalizeEmail()` (jalan sebelum `@IsEmail()`) di keempat DTO yang menerima email: `LoginDto`, `ForgotPasswordDto`, `AdminLoginDto`, `CreateInvitationDto`.
- Service menormalkan SENDIRI (tidak bergantung pada pipe): `AuthService.login/requestPasswordReset`, `AdminAuthService.login`, `AdminInvitationsService.createSingle/createBulk`. Semua kunci Redis (`login_lock`, `login_fail`, `admin_login_*`, `forgot_email`) memakai email baku. Bulk CSV kini MENYIMPAN dan melaporkan alamat baku (sebelumnya hanya kunci deteksi-duplikat yang huruf kecil, alamat yang tersimpan tidak).
- **Migrasi `20260929053000_emails_lowercase`**: membereskan data yang ada (`lower()` pada `users`/`admin_users`/`invitations`) lalu memasang `CHECK (email !~ '[A-Z]')` di ketiga tabel sebagai lapisan TERAKHIR -- jalur kode atau skrip mana pun yang lupa menormalkan GAGAL KERAS, bukan diam-diam membuat alamat kembar. CHECK sengaja hanya melarang huruf ASCII besar, bukan `email = lower(email)`: `lower()` Postgres untuk karakter non-ASCII bergantung pada locale/libc dan bisa berbeda dari `toLowerCase()` aplikasi sehingga menolak nilai sah yang sudah dinormalkan (Postgres 17 di Alpine/musl: `lower('ÀBC')` = `àbc`, `'É' ~ '[A-Z]'` = false -- diuji). Alamat kembar yang HANYA beda kapitalisasi di `users`/`admin_users` tidak bisa diselesaikan otomatis: migrasi berhenti dengan pesan Indonesia yang jelas (bukan galat unique constraint yang membingungkan).
- Penjaga statis baru di `controller-input-guard.test.ts`: setiap properti `@IsEmail` di DTO controller WAJIB juga `@NormalizeEmail` (punya self-test; audit atas controller asli lulus).

**2. `POST /auth/forgot` (tanpa login, memicu EMAIL ke alamat pilihan pemanggil) dibatasi dua lapis** (konstanta + alasan di `auth/auth.const.ts`):
- **Per alamat, di Redis (3 per jam, semua klien digabung)** -- mencegah kotak surat satu orang dibanjiri. Jendela tetap: `SET key 0 EX 3600 NX` LEBIH DULU lalu `INCR` (kunci selalu punya TTL; `INCR` lalu `EXPIRE` terpisah bisa meninggalkan kunci abadi kalau proses mati di antaranya). Melebihi batas = email TIDAK dikirim, tetapi jawabannya tetap 200 dengan badan yang identik (anti-enumerasi: "dibatasi" tak boleh terlihat berbeda dari "terkirim" maupun "tak terdaftar"); alamat tak terdaftar dihitung sama persis, dan penghitungan terjadi SEBELUM query DB. Peringatan log memuat rujukan hash pendek, bukan alamat email (PII).
- **Per IP (`@Throttle`, 30 per jam → 429)** -- mencegah satu klien menyemprot banyak alamat. Cukup longgar untuk satu kelas di belakang NAT yang sama. Penyimpanannya di MEMORI proses (bawaan `ThrottlerModule`): kalau API dijalankan lebih dari satu instance, batas ini menjadi per instance -- pindahkan ke storage Redis milik throttler sebelum scale-out.
- **Reset yang dipicu admin (ADM-22) memakai jalur yang sama** (`AuthService.requestPasswordReset` mengembalikan `SENT | THROTTLED | UNKNOWN_EMAIL`; endpoint publik membuangnya). Admin sudah terautentikasi dan barisnya pasti ada, jadi kena batas dijawab JUJUR: 429 + "Reset password untuk murid ini sudah diminta terlalu sering (maksimal 3 kali per jam)" -- dan halaman detail murid admin menampilkan pesan itu (bukan "Gagal" generik). Menjawab "terkirim" padahal tidak akan menyesatkan admin.
- Layar "Cek Emailmu" (murid) kini menyebut bahwa permintaan dibatasi per jam dan menyarankan memakai tautan dari email terbaru -- tanpa angka, sama untuk semua alamat, jadi tidak membocorkan apa pun.

**3. `TRUST_PROXY` (env baru, opsional).** Pembatas per-IP membaca `req.ip`. Di belakang reverse proxy tanpa setelan ini SEMUA klien tampak berasal dari IP proxy: pembatas per-IP menjadi SATU jatah untuk seluruh pengguna (mis. 30 lupa-password per jam untuk seluruh lembaga; hal yang sama sudah berlaku bagi `request-resend` 3/jam dan default global 100/menit). `common/trust-proxy.ts` `parseTrustProxy`: kosong/`0`/`false` → tanpa proxy (dev); bilangan bulat N → percaya N hop; string lain → daftar subnet Express (alamat tak valid membuat boot gagal); **`true` DITOLAK saat boot** karena mempercayai setiap header `X-Forwarded-For` yang bisa dipalsukan klien untuk melewati semua pembatas. **Produksi di belakang proxy WAJIB mengisinya** (mis. `TRUST_PROXY=1`); tercatat di `.env.example`.

**4. Sampingan:** `ProfilePage` menangani gangguan jaringan pada `PATCH /me` (dulu tombol macet di "Menyimpan..." tanpa pesan; kini pola `try/catch` + `failureText` seperti `LoginPage`, dengan pesan 429/5xx/jaringan yang tepat dan `role="alert"`).

`createApiClient` membungkus `openapi-fetch` (bukan re-invent typed-fetch-client sendiri, sesuai rencana asli poin 7) dengan SATU middleware (`onRequest`+`onResponse`) yang menangani:
- **Lampirkan `Authorization: Bearer <access token>`** ke tiap request dari `tokenStorage`.
- **401 → refresh sekali → retry request YANG SAMA** (bukan request baru) -- `onRequest` meng-clone `Request` MENTAH (sebelum body-nya "dipakai" fetch asli, `Request` itu stream sekali-pakai) dan menyimpannya per-id request; `onResponse` yang lihat 401 memakai clone itu untuk retry via `fetch()` mentah (BUKAN lewat client lagi -- sengaja, supaya tidak ada risiko retry-loop). Body POST/PATCH ikut selamat lewat retry (dites eksplisit, lihat di bawah).
- **Refresh token itu ROTATE-ON-USE + deteksi-reuse di server** (`AuthService.refresh`/`AdminAuthService.refresh`, sudah ada sejak Milestone 5) -- dua request PARALEL yang sama-sama 401 di saat yang sama (mis. React StrictMode me-render ganda, atau beberapa panggilan API di satu halaman) TIDAK BOLEH masing-masing manggil `/auth/refresh` sendiri-sendiri, refresh token yang SAMA dipakai dua kali akan membuat salah satunya "reuse" dan me-revoke SELURUH chain. - **Refresh sendiri gagal** (refresh token juga sudah tidak valid) → `tokenStorage.clear()` + callback `onUnauthenticated` (per-app: `window.location.assign('/login')` hard-navigation, di luar konteks router karena dipanggil dari modul non-komponen).

**Bug nyata ketemu+diperbaiki lewat unit test yang GAGAL duluan** (bukan lewat baca kode/reasoning saja -- pola sama seperti bug `ScenarioSession.next()` bagian 6d): draf pertama `doRefresh()` manggil `fetch(urlString, init)` (string mentah, bukan objek `Request`) -- test mock yang seragam mengasumsikan SEMUA panggilan `fetch()` menerima `Request` (`req.url`) langsung crash diam-diam kena `new URL(undefined)` di dalam mock, ketangkep `try/catch` `doRefresh` sendiri, jadi refresh "gagal" tanpa pernah benar-benar menyentuh mock endpoint refresh -- 4 dari 6 test gagal dengan gejala yang awalnya terlihat seperti bug di RETRY logic, padahal itu di TEST HARNESS. Ketahuan dengan skrip debug bertahap (isolasi tiap lapis: id-matching → clone → retry fetch) sampai ketemu `req.url` yang `undefined`. **Diperbaiki**: `doRefresh()` sekarang selalu `fetch(new Request(url, init))` eksplisit -- SEMUA panggilan `fetch()` di client ini (request asli lewat `openapi-fetch`, refresh, retry) sekarang konsisten selalu menerima objek `Request` genuine, bukan campuran string/Request.

**`AuthGuard` sungguhan** (kedua app, pola identik): BUKAN cuma cek `localStorage` kosong/tidak seperti stub sebelumnya -- panggil `GET /me` (murid) / `GET /admin/auth/me` (admin) SUNGGUHAN saat mount. **Perilaku halaman (keputusan yang perlu diketahui):**
- **`/invite/:token`** memeriksa token ke server dulu (`checking` → form / halaman status / "tidak terjangkau" + "Coba Lagi"). Form: nama (terisi dari undangan, boleh diubah, dipangkas), email TERKUNCI (readonly, dari undangan), password + konfirmasi (validasi klien memakai aturan domain; server tetap penegak akhir). **Body registrasi hanya `{token, name, password}`** -- `classId`/`email` diturunkan server dari undangan (dan server menolak 400 kalau klien menyelundupkannya, dibuktikan di stack nyata). Sukses = auto-login lalu `/welcome`. 400 dengan pesan bisnis (`string`: undangan berubah sejak halaman dibuka) memicu pemeriksaan ulang, jadi murid melihat halaman yang sesuai (mis. "Undangan sudah dicabut"), bukan form yang pasti gagal lagi.
- **Tombol "Minta undangan ulang" hanya untuk `EXPIRED`** -- deviasi dari bunyi AC AUTH-02 ("token invalid/kedaluwarsa"): untuk token yang tak dikenal server tidak tahu siapa yang harus diberi tahu (endpoint-nya memang diam-diam tidak melakukan apa-apa), dan undangan `REVOKED` sengaja dicabut admin. `NOT_FOUND` memberi petunjuk memakai tautan email terbaru (admin "kirim ulang" mengganti token, tautan lama jadi `NOT_FOUND`) dan menghubungi admin. Perlu konfirmasi PO.
- **`/forgot-password`** -- server SELALU membalas 200 (anti-enumerasi), maka layar "Cek Emailmu" sengaja BERSYARAT ("Kalau X terdaftar, ...") dan identik untuk email terdaftar maupun tidak (dibuktikan: tidak ada email/baris token untuk alamat tak terdaftar). 400 (bentuk email salah) → "Format email tidak valid."
- **`/reset-password/:token`** -- tidak ada endpoint pra-cek token reset, jadi tautan kedaluwarsa/terpakai baru ketahuan saat submit; pada kasus itu halaman berganti ke "Tautan Reset Tidak Berlaku" + tombol minta tautan baru (bukan error mentah). Sukses → `tokenStorage.clear()` (reset mencabut SEMUA refresh token di server; token yang tersisa di perangkat sudah mati dan akan memantulkan `/login` ke sesi mati) → `/login` dengan banner "Password berhasil diubah".
- **`/welcome`** -- 3 langkah: (1) target XP harian 10/30/50 -- benar-benar disimpan lewat `PATCH /me` (hanya bila berubah; gagal = tetap di langkah 1 dengan pesan); (2) level dibaca dari `GET /path` (gagal = pesan lembut, onboarding tetap bisa diselesaikan); (3) ringkasan → "Mulai Belajar" ke Beranda. **Tes penempatan (AUTH-05, opsional) BELUM ADA** sehingga murid selalu mulai dari awal jalur, dan **tidak ada penanda "sudah onboarding" di server** -- halaman ini bisa dibuka lagi kapan saja lewat `/welcome`. Tidak ada yang dijanjikan di layar yang tidak nyata.
- **Pesan error**: klien tidak menampilkan pesan validasi server (Inggris, `string[]`). `failureText` meneruskan HANYA pesan bisnis `string` dari 400 (sudah Indonesia); 429 → "Terlalu banyak percobaan...", ≥500 → "Terjadi gangguan di server...", gangguan jaringan (fetch melempar) → pesan jaringan; selebihnya teks tetap per layar. Ini sekaligus menjawab butir PO lama soal pesan validasi form publik.
